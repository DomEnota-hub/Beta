## Further semantic triage: state and content boundaries

- `MainActivity.kt` in the archive reads `accent_palette` from SharedPreferences `appearance`; the pinned later donor reads `accent_palette` and `theme_mode` from `calculation_inputs`. In the old `Theme.kt`, enum `BLUE` displays amber; in the later `Theme.kt`, `BLUE` displays blue and `AMBER` is a distinct enum. Copying the stored enum name or changing the preference file without an explicit compatibility rule can silently change the user's chosen appearance. This is a **migration gap**, not proof that a user's data was lost. Preserve the old preference bytes and test an in-place signed upgrade before defining a mapping; no palette value is migrated by this review.
- `LocomotiveProfileRepository.kt` retains the old `locomotive_profile` file and `selected_profile` / `selected_variant` keys. The later donor adds a separate diagnostic context and invalidates its confirmation when the UI selection changes. A selected locomotive is not evidence of a confirmed diagnostic execution. `SecretAccessRepository.kt` has an explicit old-state migration path; its behavior and access policy still require separate functional tests. These repository files are not independent technical source records.
- `KnowledgeRepository.kt` contains all 23 literal article IDs present in the archive and adds 19; the `vl80-layout` source note changes from “справочник” to “атлас”, and the later search separates locomotive articles, general knowledge and safety. This ID check does **not** prove all article bodies or applicability equivalent. The archive's search behavior must not be restored over the later separation without product review.
- `DiagnosticRepository.kt` retains the same 11 literal scenario IDs in that file, but replaces seven old literal question keys in the ГВ/тяга branches with a different graph; the pinned donor also adds research integration and unknown routing. The old graph must not be grafted onto the later one by key similarity. `DiagnosticDeepening.kt` extends the compressor route with a gauge question and many later routes; `DiagnosticCompletionCatalog.kt` grows from six to 15 literal scenario IDs. Each route requires node-level safety, source and variant review before any missing-content claim.
- The archive's `InteractiveSchematicsTest.kt` checks `pneumaticRoutesExposeFlowReleaseAndControl()`, while the later test omits that assertion. The function itself is present in `KnowledgeBaseScreen.kt` in **both** versions. This was a test-coverage difference; Beta's `qa/validate_vl80s_pneumatic_flows.py` now checks both `RELEASE` and `CONTROL` in release mode on code SHA `2c124a36fc610658b372d7cf7217e69fddb1a5e3`. Its full bootstrap and dedicated pneumatic CI runs completed successfully. This validates the migrated asset's segment kinds only, not physical routing.

These observations do not change the nine limited dispositions above or close the 24 remaining comparisons. They identify the next focused checks: preference compatibility, the removed pneumatic assertion, full article text and diagnostic graph semantics. No legacy runtime/UI code is promoted.
