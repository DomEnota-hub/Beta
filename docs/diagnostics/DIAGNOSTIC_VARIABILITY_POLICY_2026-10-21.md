# Диагностика — вариативность и исторические расширения

Согласовано 21.10.2026. Применяется к следующим этапам авторинга
(сохранение 340 canonical identities, без runtime promotion).

## Критерий выбора материала

Основная цель — **разные технические подходы** к одной неисправности, а
не накопление URL. Для каждого подхода фиксируются: идентичность исходной
записи, источник, исторический/текущий статус, профиль, оснащение,
признак для выбора альтернативы, другое объяснение причин, конфликт с
другим источником, роль исполнителя и допустимость предлагаемого действия.
Внутри одного источника допустимы несколько самостоятельных подходов.

Три разных явления:
1. `SOURCE_MISSING` — исходной записи для ветви действительно нет.
2. `HISTORICAL_INFORMATION_BOUND` — источник есть, версия/точная применимость
   не подтверждены; информационная ветвь может обсуждаться в расширенном
   режиме после предупреждения.
3. `CURRENT_ACTION_VERIFIED` — отдельный строгий путь проверки источника,
   установленного оборудования и права на конкретную безопасную операцию.
   В авторских пилотах этот статус не присваивается.

## Реализация и ограничения

Нормальный режим: SHORT и DETAILED содержат подготовленные и проверяемые
приёмочные сценарии, без автоматически импортируемых старых методов.

Расширенный: отдельные, по умолчанию скрытые источниковые альтернативы,
предупреждение с прокруткой до конца и подтверждение. Маркировать
«исторический», «непроверенный», «личный опыт», «не подтверждено для этого
исполнения»; не выдавать неподтверждённое как применимое к данной машине.
При конфликте двух публикаций показывать различие, не присваивая
«правильный» метод без доказательств.

Предупреждение НЕ разрешает операцию. Метод обхода защиты и действие,
доступное только другой профессии, не становится исполняемой рекомендацией,
даже если это старый опубликованный совет. Иначе пользователь ошибочно
воспримет материал как допуск. Можно сохранить источник и сам факт
расхождения как ограниченный исторический контекст.

Критерии preflight: уникальность `approachId`, допустимость нескольких
`approachId` на один `sourceId`, независимость графов двух версий,
источниковая трассировка, границы профиля, запрет повышения
`actionAuthorityGranted`, запрет пропуска предупреждения. Нормативная
достоверность и безопасная семантика отдельных путей всё ещё требуют
человеческой проверки: структурные тесты не обнаруживают опасные советы,
написанные свободным текстом.

Источник — граф — версия — уровень доверия — отображение — полномочие
на действие остаются шестью самостоятельными осями.

## Результат двух пилотов

- ВЛ80С: два SHORT и три DETAILED исторических подхода.
- ЧМЭ3Т: два SHORT и три DETAILED исторических подхода.
- Основные графы 8/18 и 10/18 узлов не заменены, запрещённые
  эксплуатационные действия не импортированы.
- Android UI и реальная публикация ещё не подключены; этот этап
  готовит данные и контракт, а не выпускает исторические методы
  автоматически для машиниста.

## Продолжение

Для этапов после пилотов сначала строить карту **различающихся решений**
по неисправности (несколько источников могут подтверждать один подход,
один источник может содержать несколько подходов). Приоритет выбирать по
диагностической ценности и степени различия, затем по доступности
проверяемых источников, не наоборот. При расширенном варианте
комплексность нормативной проверки не должна быть условием отображения
**информационного** материала, но источниковая идентичность и
соблюдение границ безопасности обязательны.
